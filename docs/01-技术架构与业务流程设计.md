# 某商业银行银行纪念币预约系统 — 技术架构与业务流程设计

> 版本：v2.0（已确认核心决策）
> 目标：支撑瞬时百万级并发，严格防超卖/防超限购，高可用。

---

## 一、需求与核心目标

| 维度 | 要求 |
|------|------|
| 并发量 | 瞬时百万级并发（开闸提交预约意向的瞬间） |
| 抢约模式 | **实名预填 + 抽签/排队**（银行类业务常用，先验资格、后分配额度） |
| 正确性 | **防超卖**、**防超限购**（每人限购 N 套）、幂等防重 |
| 实名 | 一个身份证仅可预约一次（同一产品，跨网点），需实名预填 + 三要素校验 |
| 网点分配 | **按网点分配额度**，客户预约必须选网点，网点额度约满即止 |
| 高可用 | 核心链路无单点，网关/预约服务/Redis/Kafka 均可水平扩展 |
| 最终一致 | 中签结果落库允许短暂延迟，最终一致 |

**核心思路转变**：抽签/排队模式下，**「提交预约」与「扣减库存」解耦**——提交瞬间只做「资格校验 + 入队/入池」，库存扣减延后到「抽签/分配阶段」低并发地执行。这从根本上缓解了「百万并发 + 防超卖」这对矛盾。

**组件职责边界（关键）**：
- **Redis**：资格校验缓存、幂等去重、排队/抽签池（List / Sorted Set / Set）、限购计数、**库存原子扣减**、序号号段。
- **Kafka**：中签/结果事件的**可靠异步落库管道**（削峰解耦 DB），不承载峰值入队（峰值入队走 Redis，见 4.2）。

## 三、微服务拆分

| 服务 | 职责 | 关键点 |
|------|------|--------|
| **gateway-service** | 统一入口：鉴权、限流、路由、熔断、幂等 Token、黑名单 | WebFlux 非阻塞，无业务逻辑 |
| **coin-reservation-service ★** | 预约核心：实名资格校验、入队/入池、抽签/排队分配、网点库存原子扣减、发 Kafka、库存回补；预约取消/修改 | 无状态可水平扩展；含分配定时任务/消费者 |
| user-service | 用户信息、实名认证（身份证三要素校验） | 提供实名结果供资格校验 |
| product-service | 产品/活动信息、**网点额度配置**、开闸/截止/抽签时间、额度配置 | 活动信息预热进 Redis |
| order-service | 消费 Kafka 中签事件落库、生成中签记录、**预约明细查询**/通知 | 写多读多，读写分离（1主2从） |
| exchange-service | 线下柜面**预约兑换登记**（校验预约+网点+状态，标记已兑换，写兑换流水） | 低频，柜面渠道，权限隔离 |
| 基础组件 | Nacos、Sentinel、SkyWalking、Prometheus | 注册/配置/治理 |

> 峰值主链路：`gateway → reservation-service → Redis`（资格校验 + 入队），**不依赖 DB、不依赖 Kafka 同步阻塞**。

## 四、核心技术方案

### 4.1 防超卖（三层防线）

库存扣减发生在**抽签/分配阶段**（低并发），但防线不变：

#### 第 1 层：Redis Lua 原子扣减（主防线，库存按「商品 × 网点」维度）
```lua
-- KEYS[1] = 网点库存key(branchId)   KEYS[2] = 用户限购Hash key
-- ARGV[1] = idCard/用户标识          ARGV[2] = 限购数量上限
local stock = tonumber(redis.call('get', KEYS[1]) or '0')
if stock <= 0 then
  return -1            -- 库存不足
end
local bought = tonumber(redis.call('hget', KEYS[2], ARGV[1]) or '0')
if bought >= tonumber(ARGV[2]) then
  return -2            -- 超过限购
end
redis.call('decr', KEYS[1])
redis.call('hincrby', KEYS[2], ARGV[1], 1)
return 1               -- 中签成功（预扣）
```

#### 第 2 层：幂等防重
- 提交预约带一次性幂等 Token，`SET key NX EX` 去重，防重复提交/网络重试。

#### 第 3 层：DB 唯一约束 + 乐观锁兜底
- `t_reservation` 唯一约束 `(product_id, id_card)`（跨网点一人一套），落库时拒绝重复/超发。
- `t_branch_stock`（商品 × 网点）用 `version` 乐观锁 + `remain>0` 条件扣减，保证**网点不超卖**；定时对账 Redis vs PG。

> **为何抽签模式更稳**：中签数量先确定（≤ 库存），再逐个原子扣减；即使 Redis 中途异常，DB 唯一索引 + 对账也能兜底，**超卖恒为 0**。

### 4.2 百万并发支撑（峰值只在「资格校验 + 入队」）

开闸瞬间的百万并发发生在**提交阶段**，此时只做纯 KV 操作，无库存热点竞争：

| 手段 | 说明 |
|------|------|
| 网关多级限流 | 全局总限流 → IP 限流 → 用户限流（Sentinel + Redis 分布式计数） |
| 无状态水平扩展 | gateway / reservation 服务按 QPS 横向扩容 |
| 队列/资格池分片 | 排队池、抽签池、限购计数按 `userId` 哈希分片到多 key，**消除单一热点 key** |
| 网点库存分片 | 热门网点库存拆多分片，按 `userId` 哈希路由扣减，**消除网点热点 key** |
| 序号号段预取 | 排队序号由 Redis 基准 + 实例本地批量预取号段生成（Leaf 思想），避免 INCR 单点热点 |
| 资格本地缓存 | 实名资格校验结果本地缓存（Caffeine）+ Redis，减少远程调用 |
| Redis Cluster | 分片 + 主从，读写分离，故障自动切换 |
| Kafka 削峰 | 中签结果异步写 Kafka 落库，DB 压力与峰值解耦 |

> **关键**：峰值阶段不扣库存、不写 DB，只做「读资格 + 写入队」的 KV 操作，单实例可支撑数万~十数万 QPS，水平扩展达成百万级。

### 4.3 抽签 / 排队 双模式（可配置）

| 模式 | 入队数据结构 | 分配方式 | 适用 |
|------|-------------|----------|------|
| **排队**（先到先得） | Redis Sorted Set（score=全局序号） | 按序号升序 `ZPOPMIN` 逐个分配 | 强调先来后到 |
| **抽签**（公平随机） | Redis Set（资格池，分片） | 截止后 `SPOP` 随机抽取 | 强调公平 |

- 两种模式共用一个「分配器」：弹出成员 → Lua 原子扣库存 → 成功发 Kafka 中签消息 → 失败（库存尽）停止。
- 模式由活动配置 `draw_mode` 决定，`coin-reservation-service` 内实现，可扩展为「排队抽签混合」。

### 4.4 限流与降级（Sentinel）
- 网关层：QPS 限流、并发线程数限流、热点参数限流（对 hot 商品 ID）。
- 预约服务层：Sentinel 熔断 Redis/Kafka 异常，快速失败，避免雪崩。
- 降级策略：资格校验失败直接拒绝；Redis 异常时降级为「系统繁忙」，绝不击穿 DB。

### 4.5 事务回滚与分布式一致性（核心）

**先认清本质**：Redis 与 PostgreSQL 是两种独立存储，Redis 不支持 ACID，也不参与 XA 分布式事务。因此 **「Redis 与 PG 一起回滚」无法用数据库事务实现**，只能分层处理：

| 边界 | 机制 | 是否「真回滚」 |
|------|------|---------------|
| PostgreSQL 内部（落库事务） | 本地 ACID 事务（`@Transactional`） | ✅ 真回滚（rollback） |
| Redis 内部（扣库存 + 扣限购） | Lua 原子脚本 | ✅ 原子，无中间态 |
| Redis ↔ PostgreSQL 跨库 | **补偿 + 幂等 + 对账** | ⚠️ 补偿式回滚，最终一致 |

#### 中签单状态机（贯穿 orderNo）
```
PRE_DEDUCTED（Redis 已预扣库存+限购）
     │  发 Kafka RESV_RESULT
     ▼
order-service 落库
     ├─ PG 事务成功 ──────────▶ CONFIRMED（t_reservation 已落库）
     └─ PG 事务失败/超时 ──────▶ COMPENSATED（Redis 已回补库存+限购）
```

#### 一致性完整流程
```
分配器(reservation-service):
  ① Lua 扣 Redis「库存 + 限购」→ 成功 → 生成 orderNo → 状态 PRE_DEDUCTED
  ② 发 Kafka RESV_RESULT
order-service 消费:
  ③ 开 PG 本地事务:
       INSERT t_reservation（唯一约束兜底）
       UPDATE t_branch_stock SET remain=remain-1, version=version+1
        WHERE product_id=? AND branch_id=? AND remain>0
     - 成功 → COMMIT → 状态 CONFIRMED
     - 失败 → ROLLBACK（ACID 自动回滚）→ 状态 COMPENSATED
  ④ PG 事务失败 → 触发「Redis 补偿」回补库存 + 回退限购
```

#### PostgreSQL 回滚（本地事务，ACID）
```java
@Transactional(rollbackFor = Exception.class)
public void confirmReservation(Reservation r) {
    int inserted = reservationMapper.insert(r);        // 唯一约束冲突 → 抛异常回滚
    int updated  = stockMapper.deduct(r.getProductId(), r.getBranchId()); // remain>0 条件，0 行 → 抛异常回滚
    if (inserted != 1 || updated != 1) {
        throw new BizException("落库失败，事务整体回滚");
    }
    // 方法正常返回 → COMMIT；抛异常 → 两个语句一起 ROLLBACK
}
```

#### Redis 回滚（补偿 Lua，与扣减脚本严格对称）
```lua
-- 补偿：库存 +1，限购 -1（仅当该用户确实扣过才执行）
redis.call('incr', KEYS[1])                 -- 库存回补
redis.call('hincrby', KEYS[2], ARGV[1], -1) -- 限购回退
```

#### 关键风险与规避（最容易被忽略的点）

**风险**：PG 事务已 COMMIT 成功，但响应超时 → 触发补偿回补了 Redis → 结果 PG 里有一单、Redis 库存却被加回 → 超卖 1 个。

**规避（四道保险）**：
1. **PG 是最终真相**：`t_reservation` 唯一约束 `(product_id, id_card)` 拒绝重复；`t_branch_stock.remain>0` 乐观条件拒绝网点超扣——PG 层永远不会超卖。
2. **补偿前先查 PG**：回补 Redis 前先查 `t_reservation` 是否已存在该 `orderNo`，已存在则**不回补**（说明 PG 实际成功）。
3. **幂等补偿**：回补用「补偿标记」去重，防止重复回补导致库存被多加。
4. **定时对账兜底**：扫描 `PRE_DEDUCTED` 且超时未确认的 orderNo → 查 PG → 未落库则回补 Redis，已落库则置 CONFIRMED。

#### 失败场景回滚矩阵

| 失败点 | PostgreSQL 动作 | Redis 动作 |
|--------|----------------|-----------|
| ① Lua 扣减失败（库存尽/超限购） | 不涉及 | 无副作用（Lua 内原子判断后直接返回） |
| ② Kafka 投递失败/超时 | 不涉及 | 回补库存 + 限购（补偿 Lua） |
| ③ PG 落库失败（唯一冲突/库存0/DB 挂） | 事务自动 ROLLBACK | 回补库存 + 限购（补偿 Lua） |
| ④ PG 提交成功但响应超时 | COMMIT 已生效 | 先查 PG，已落库则**不回补** |
| ⑤ 消费端重复消费 | 唯一约束拒绝重复 | 幂等，不重复回补 |
| ⑥ 分配器崩溃 | 未完成订单由对账兜底 | 对账回补 |

> **一句话总结**：PostgreSQL 用「事务」做真回滚，Redis 用「补偿 Lua」做回滚，两者之间靠「补偿前先查 + 幂等 + 定时对账」保证最终一致，超卖恒为 0、库存不丢不重。

### 4.6 Redis 故障的 DB 兜底降级方案

**定位澄清（必须先说清）**：DB 兜底是**「降级保可用」，不是「替代 Redis 扛百万并发」**。单 PostgreSQL 主库写吞吐约 5000~1 万 TPS，与百万 QPS 相差 1~2 个数量级。因此 Redis 挂时必须三管齐下：
1. **强限流**：Sentinel 令牌桶把并发压到 DB 容量以内；
2. **业务降级**：提示「系统繁忙/请稍后再试」，必要时转为排队；
3. **绝不裸奔**：不让 DB 直接暴露在峰值流量下，否则 DB 必被打垮。

#### 单库 1主2从 + 不分库分表（当前架构）

- 写走**主库**，读走 **2 个从库**（预约明细查询、兑换查询等读多走从库）。
- 不分库分表 → 唯一约束 `(product_id, id_card)` 与乐观锁 `remain>0` 天然在**单库内**成立，防超卖/防超限购无需跨库处理。
- **单库最大优势**：「扣网点库存 + 写预约记录」在**同一个数据库事务**内完成，一致性实现最简单、最可靠（无需分库分表下的跨库补偿）。

#### DB 直扣防超卖（降级模式，单库事务）
```sql
-- 同一事务内：
-- 1) 网点库存扣减：乐观条件，affected=0 → 该网点已约满
UPDATE t_branch_stock
   SET remain = remain - 1, version = version + 1
 WHERE product_id = ? AND branch_id = ? AND remain > 0;

-- 2) 写预约记录：唯一约束冲突 → 该身份证已约过（防超限购）
INSERT INTO t_reservation(order_no, product_id, branch_id, user_id, id_card, status, create_time)
VALUES (?, ?, ?, ?, ?, 1, now());
-- 任一失败 → 事务整体回滚，无需跨库补偿
```

#### 切换与恢复流程
```
① 检测：Sentinel/健康检查判定 Redis 不可用
② 切换：网关/服务自动切「DB 直扣」降级模式 + 强限流（压到主库容量内）
③ 运行：主库单库事务直扣 PG，防超卖靠乐观锁 + 唯一约束
④ 恢复：Redis 恢复后，用 PG 数据重建 Redis 库存（对账），切回 Redis 主模式
```

#### 单库下的容量与可用性对策
| 风险 | 对策 |
|------|------|
| 主库写单点 | 自动故障切换（Patroni / Repmgr），主挂切从，切换窗口秒~分钟级 |
| 写吞吐瓶颈 | 异步落库 + 最终一致；落库慢不影响预约成功率 |
| 单表膨胀 | 按活动/年度**归档历史数据**，控制单表体量 |
| 读压力 | 读走 2 从库；关键状态查询走主库，非关键走从库 |
| 主从延迟 | 关键一致性读走主库，避免读到旧状态 |

> **一句话总结**：Redis 挂了 → 降级为「DB 直扣 + 强限流」，单库事务（乐观锁 + 唯一约束）防超卖；单库保「正确性」最简，瓶颈只在「写吞吐 + 写单点」，靠异步落库 + 归档 + 主从切换缓解。

## 五、业务流程设计（四阶段）

### 阶段 0：活动准备（预热）
1. product-service 发布活动，配置**各网点额度**、开闸/截止/抽签时间、限购、模式。
2. 网点库存（商品 × 网点）写入 Redis（分片），产品/网点信息预热进 Redis/本地缓存。

### 阶段 1：实名预填（开闸前）
```
用户提交实名(姓名/身份证/手机) → user-service 三要素校验 → 写入 t_qualification(唯一索引 id_card)
                                                              → Redis 标记已实名
```
- 未实名预填通过的用户，开闸时无法提交预约。

### 阶段 2：资格校验 + 入队（开闸瞬间 = 百万并发峰值）

```
客户端 → gateway(鉴权+限流) → reservation-service
  1. 幂等去重(SETNX token)
  2. 资格校验：已实名预填 ✓ | 未超限购 ✓ | 未重复提交 ✓ | 非黑名单 ✓
  3. 入队/入池（携带所选网点 branchId）：
     校验网点：网点存在且该网点额度未满
     排队模式 → 生成全局序号 → ZADD queue:{productId}:{shard} score=seq member=userId
     抽签模式 → SADD pool:{productId}:{shard} userId
  4. 秒回「已受理，进入抽签/排队」
```
- **本阶段不扣库存、不写 DB**，纯 KV 校验 + 写入队。

### 阶段 3：抽签 / 分配（截止后，异步、可控）
```
分配器(reservation-service 定时任务/消费者)：
  弹出成员(排队:ZPOPMIN 按序 / 抽签:SPOP 随机)
  → Lua 原子扣「该用户所选网点的库存」 + 限购
  → 成功：发 Kafka 中签消息 RESV_RESULT（含 branchId）
  → 失败(该网点库存尽/超限购)：停止 / 标记未中
```
- 分配在截止后**低并发**执行，库存扣减无热点压力。

### 阶段 4：中签落库 + 通知
```
order-service 消费 Kafka RESV_RESULT
  → 幂等校验(orderNo)
  → INSERT t_reservation(唯一索引兜底)
  → 更新 t_branch_stock(乐观锁)
  → 通知用户(短信/推送/站内信) + 前端查询可查结果
```

### 异常与兜底矩阵

| 场景 | 处理 |
|------|------|
| Redis 挂/超时 | Sentinel 熔断 + 切「DB 直扣」降级模式（见 4.6），强限流保可用 |
| Kafka 不可用 | 本地重试 + 失败回补库存（Lua INCR/HINCRBY-1） |
| DB 写入失败 | PG 事务 ROLLBACK + Kafka 消费重试 + 死信 + 定时补偿 |
| Redis 预扣后 PG 落库失败 | 见 4.5：PG 回滚 + Redis 补偿回补（先查后补 + 幂等） |
| 重复请求/网络重试 | 幂等 Token + 预约单唯一约束双保险 |
| 分配中断 | 断点续跑（记录分配游标），未分配成员不丢 |
| 分片不均 | 分配器聚合各分片；定时对账 Redis vs PG 库存 |

### 5.5 配套业务功能（查询 / 取消 / 修改 / 兑换）

预约单状态机：
```
1 已预约(待兑换) ──取消──▶ 2 已取消
1 已预约(待兑换) ──修改──▶ 4 已修改(原单作废，生成新单/更新网点)
1 已预约(待兑换) ──兑换──▶ 3 已兑换
```

#### 5.5.1 预约明细查询（高频读）
- 按 `id_card` / `user_id` 查 `t_reservation`（单库查询）。
- 热数据走 Redis 缓存（`resv:detail:{orderNo}` / 按用户维度），读多写少。
- 提供：我的预约列表、单条详情、当前状态。

#### 5.5.2 预约取消（低频写）
- 前置校验：预约存在、状态=已预约、未兑换。
- PG 事务：`UPDATE t_reservation SET status=2 WHERE order_no=? AND status=1`。
- 释放额度：网点库存 +1（Redis INCR / DB `remain+1`）+ 限购 -1（`HINCRBY -1`）。
- 一致性：与 4.5 同构（先改状态 → 回补额度 → 失败补偿 + 幂等），取消后额度释放可再约。

#### 5.5.3 预约修改（低频写，主要是改网点）
- 本质：换网点 = **原网点库存回补 + 新网点库存扣减** + 更新 `branch_id`。
- 防超卖：新网点可能已满，扣减失败 → 修改失败，原预约保持不变。
- 限购：同一人，**不重复扣限购**，仅转移网点库存。
- 实现：Redis Lua 原子「原网点 +1、新网点 -1（先判 >0）」；DB 侧用事务 + 乐观锁。
- 窗口限制：通常仅开闸后一段时间内（如 1 小时）允许修改。

#### 5.5.4 预约兑换登记（线下柜面，低频）
- 柜员输入身份证/预约单号 → 查询预约 → 校验：**网点匹配、状态=已预约、未兑换**。
- PG 事务：`UPDATE t_reservation SET status=3` + `INSERT t_exchange`（兑换流水）。
- 防重复兑换：状态机 + `t_exchange` 唯一约束（order_no）。
- 独立 `exchange-service`（柜面渠道，权限隔离，与线上抢约流量解耦）。

## 六、数据模型设计（PostgreSQL）

```sql
-- 网点表（基础数据，通常由核心系统同步）
CREATE TABLE t_branch (
  id            BIGSERIAL PRIMARY KEY,
  branch_code   VARCHAR(32)  NOT NULL,
  branch_name   VARCHAR(128) NOT NULL,
  address       VARCHAR(256),
  status        SMALLINT NOT NULL DEFAULT 1,   -- 1营业 2停业
  CONSTRAINT uk_branch_code UNIQUE (branch_code)
);

-- 实名资格表（阶段1，唯一约束防重复）
CREATE TABLE t_qualification (
  id            BIGSERIAL PRIMARY KEY,
  user_id       BIGINT NOT NULL,
  id_card       VARCHAR(32) NOT NULL,
  name          VARCHAR(64) NOT NULL,
  phone         VARCHAR(20),
  status        SMALLINT NOT NULL DEFAULT 1,   -- 1校验通过 2未通过
  create_time   TIMESTAMP NOT NULL DEFAULT now(),
  CONSTRAINT uk_qualification_idcard UNIQUE (id_card)
);

-- 产品/额度表（总发行量；网点额度在 t_branch_stock）
CREATE TABLE t_product (
  id              BIGSERIAL PRIMARY KEY,
  product_code    VARCHAR(64)  NOT NULL,
  name            VARCHAR(128) NOT NULL,
  total_stock     BIGINT       NOT NULL,       -- 总发行量
  limit_per_user  INT          NOT NULL DEFAULT 1,
  draw_mode       SMALLINT     NOT NULL DEFAULT 1, -- 1排队 2抽签
  submit_start    TIMESTAMP    NOT NULL,  -- 开闸(提交开始)
  submit_end      TIMESTAMP    NOT NULL,  -- 截止(提交结束)
  draw_time       TIMESTAMP    NOT NULL,  -- 抽签/分配时间
  status          SMALLINT     NOT NULL DEFAULT 0,
  CONSTRAINT uk_product_code UNIQUE (product_code)
);

-- 网点库存表（商品 × 网点，乐观锁防网点超卖）
CREATE TABLE t_branch_stock (
  id            BIGSERIAL PRIMARY KEY,
  product_id    BIGINT NOT NULL,
  branch_id     BIGINT NOT NULL,
  total         BIGINT NOT NULL,               -- 该网点额度
  remain        BIGINT NOT NULL,               -- 该网点剩余
  version       BIGINT NOT NULL DEFAULT 0,     -- 乐观锁
  CONSTRAINT uk_branch_stock UNIQUE (product_id, branch_id)
);

-- 中签/预约结果表（防超卖/超限购兜底：唯一约束）
CREATE TABLE t_reservation (
  id            BIGINT PRIMARY KEY,          -- 雪花ID（应用层生成）
  order_no      VARCHAR(64) NOT NULL,        -- 中签/预约单号
  product_id    BIGINT NOT NULL,
  branch_id     BIGINT NOT NULL,             -- 预约网点
  user_id       BIGINT NOT NULL,
  id_card       VARCHAR(32) NOT NULL,
  sequence_no   BIGINT,                      -- 排队序号(排队模式)
  status        SMALLINT NOT NULL DEFAULT 1, -- 1已预约 2已取消 3已兑换 4已修改
  create_time   TIMESTAMP NOT NULL DEFAULT now(),
  update_time   TIMESTAMP NOT NULL DEFAULT now(),
  CONSTRAINT uk_reservation_orderno UNIQUE (order_no),
  CONSTRAINT uk_reservation_product_idcard UNIQUE (product_id, id_card)  -- 跨网点一人一套
);

-- 兑换登记表（线下兑换流水，防重复兑换）
CREATE TABLE t_exchange (
  id            BIGSERIAL PRIMARY KEY,
  order_no      VARCHAR(64) NOT NULL,        -- 关联预约单号
  product_id    BIGINT NOT NULL,
  branch_id     BIGINT NOT NULL,             -- 实际兑换网点
  id_card       VARCHAR(32) NOT NULL,
  exchange_time TIMESTAMP NOT NULL DEFAULT now(),
  operator_id   BIGINT,                      -- 柜员ID
  status        SMALLINT NOT NULL DEFAULT 1, -- 1已兑换 2已撤销
  CONSTRAINT uk_exchange_orderno UNIQUE (order_no)
);
```

> **数据库架构：单库 1主2从，不分库分表**：
> - 写走主库，读走 2 从库（读写分离）。
> - 唯一约束 `(product_id, id_card)` 与乐观锁 `remain>0` 在单库内成立，防超卖/防超限购无需跨库处理。
> - 单表体量靠**数据归档**控制（按活动/年度归档历史预约、兑换记录）。
> - 主从切换用 Patroni / Repmgr 自动故障转移。
>
> **隔离级别**：落库事务默认 `READ COMMITTED`，配合乐观锁 `version` + 唯一约束即可满足，无需 `SERIALIZABLE`（避免性能损失）。

## 七、Redis Key 设计

| Key | 类型 | 说明 | TTL |
|-----|------|------|-----|
| `stock:{productId}:{branchId}:{shardId}` | String | 网点库存分片计数（商品 × 网点） | 活动期 |
| `resv:limit:{productId}` | Hash | field=userId → 已约数量（限购） | 活动期 |
| `resv:idempotent:{token}` | String | 提交幂等去重标记 | 10min |
| `queue:{productId}:{shardId}` | ZSet | 排队池（score=全局序号，member=userId） | 活动期 |
| `pool:{productId}:{shardId}` | Set | 抽签资格池（member=userId） | 活动期 |
| `resv:seq:{productId}` | String | 序号号段基准（INCR，实例本地预取） | 活动期 |
| `resv:pending:{productId}` | ZSet | 待确认中签单（score=时间戳，member=orderNo，供对账扫描） | 活动期 |
| `qual:ok:{userId}` | String | 实名资格缓存标记 | 1h |
| `product:info:{productId}` | String/Hash | 产品信息缓存（预热） | 活动期 |

## 八、Kafka 消息设计

| 项 | 设计 |
|----|------|
| Topic | `RESV_RESULT`（中签结果落库） |
| 消息体 | `{messageId, orderNo, productId, branchId, userId, idCard, sequenceNo, timestamp}` |
| Key | `orderNo`（保证同单分区内有序 + 幂等） |
| 消费组 | `order-consumer-group`（order-service 集群消费） |
| 分区 | 按峰值落库吞吐规划（如 16/32 分区） |
| 可靠性 | producer 手动 ACK（acks=all）+ 消费端幂等；**无事务消息，用「失败回补库存」替代** |
| 幂等 | 消费端以 `orderNo` 去重 + DB 唯一索引 |

> **Kafka 替代 RocketMQ 的说明**：Kafka 无原生事务消息，因此「扣库存成功 → 发消息」采用 **补偿式可靠投递**：投递失败/超时 → 回补库存（Lua INCR）+ 定时对账，配合消费端幂等，等价达到最终一致。
