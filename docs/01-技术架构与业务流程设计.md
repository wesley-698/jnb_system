# 某商业银行银行纪念币预约系统 — 技术架构与业务流程设计

> 版本：v3.0（对齐真实普通纪念币业务：先到先得、约满为止）
> 目标：支撑瞬时百万级并发，严格防超卖/防超限购，高可用。

---

## 一、需求与核心目标

| 维度 | 要求 |
|------|------|
| 并发量 | 瞬时百万级并发（开闸提交预约的瞬间） |
| 抢约模式 | **实名预填 + 先到先得（排队）**，约满为止；**无抽签环节** |
| 正确性 | **防超卖**、**防超限购**（每人限约一次）、幂等防重 |
| 实名 | 一个身份证仅可预约一次（同一产品，跨网点），需实名预填 + 三要素校验 |
| 网点分配 | **按网点分配额度**，客户预约必须选网点，网点额度约满即止 |
| 结果时效 | **提交那一刻即占用网点额度并返回预约号**，用户当场知道约上没有 |
| 高可用 | 核心链路无单点，网关/预约服务/Redis/Kafka 均可水平扩展 |
| 最终一致 | 预约记录的落库允许短暂延迟，最终一致（额度以 Redis 为准） |

**业务定位**：对齐人民银行普通纪念币的预约兑换方式——承办银行在**预约期内先到先得、约满为止**
（如工行「2026年贺岁币线上预约期：1月13日22时至1月14日24时……预约期内先到先得，约满为止」）。
因此核心设计是：**「提交预约」与「扣减网点额度」是同一时刻的同一件事**，
用户提交成功即拿到预约号；后续只有「人行核查 / 兑换 / 余量兑换」等下游环节，不存在「先收意向、事后抽签分配」。
（抽签/摇号只存在于贵金属纪念币的金币总公司销售渠道，不属于本系统范围。）

> 结论：`submit` 是整个预约链路的**唯一写入口**，不再需要独立的「分配/抽签」接口。

## 三、微服务拆分

| 服务 | 职责 | 关键点 |
|------|------|--------|
| **gateway-service** | 统一入口：鉴权、限流、路由、熔断、幂等 Token、黑名单 | WebFlux 非阻塞，无业务逻辑 |
| **coin-reservation-service ★** | 预约核心：活动时间窗校验、实名资格校验、**网点额度原子扣减**、发 Kafka、余量查询、额度回补；预约取消/修改 | 无状态可水平扩展；含对账定时任务 |
| user-service | 用户信息、实名认证（身份证三要素校验） | 提供实名结果供资格校验 |
| product-service | 产品/活动信息、**网点额度配置**、开闸/截止时间、额度预热 | 活动信息 + 网点清单预热进 Redis |
| order-service | 消费 Kafka 预约事件落库、**预约明细查询**/通知 | 写多读多，读写分离（1主2从） |
| exchange-service | 线下柜面**预约兑换登记**（校验预约+网点+状态，标记已兑换，写兑换流水） | 低频，柜面渠道，权限隔离 |

> 峰值主链路：`gateway → reservation-service → Redis`（时间窗校验 + 资格校验 + 原子扣额度），
> **不依赖 DB、不依赖 Kafka 同步阻塞**。

## 四、核心技术方案

### 4.1 防超卖（三层防线）

额度扣减发生在**提交那一刻**（峰值并发），因此三道防线必须在同一条路径上层层兜底：

#### 第 1 层：Redis Lua 原子扣减（主防线，额度按「商品 × 网点」维度）
```lua
-- KEYS[1] = 网点额度key(branchId)   KEYS[2] = 用户限购Hash key
-- ARGV[1] = idCard/用户标识          ARGV[2] = 限购数量上限（每人限约一次 = 1）
local stock = tonumber(redis.call('get', KEYS[1]) or '0')
if stock <= 0 then
  return -1            -- 该网点额度尽
end
local bought = tonumber(redis.call('hget', KEYS[2], ARGV[1]) or '0')
if bought >= tonumber(ARGV[2]) then
  return -2            -- 重复预约（超过每人预约次数）
end
redis.call('decr', KEYS[1])
redis.call('hincrby', KEYS[2], ARGV[1], 1)
return 1               -- 预约成功（额度已占用）
```

> 扣减与限购在**同一个 Lua 脚本**内完成，脚本整体原子，不存在「扣了额度但没记限购」的中间态。
> 同一网点的额度还要拆成 N 个分片（见 4.2），脚本只作用于一个分片，**分片间 fallback 仍限定在同一网点内**，
> 因此语义始终是「这个网点还有没有额度」。

#### 第 2 层：幂等防重
- 提交预约带一次性幂等 Token，`SET key NX EX` 去重，防重复提交/网络重试。
- **失败即释放**：若因「该网点已约满 / 无资格 / 不在预约期内」而失败，立即删除幂等键，
  否则用户换网点重试时会被「请勿重复提交」挡在门外 10 分钟。只有成功才保留幂等键。

#### 第 3 层：DB 唯一约束 + 乐观锁兜底
- `t_reservation` 唯一约束 `(product_id, id_card)`（跨网点一人一套），落库时拒绝重复/超发。
- `t_branch_stock`（商品 × 网点）用 `version` 乐观锁 + `remain>0` 条件扣减，保证**网点不超卖**；定时对账 Redis vs PG。

#### 第 4 层：在途单对账 + 幂等回补
- 额度是在**扣减成功之后、投递 Kafka 之前**写入在途单（`resv:pending:{productId}`）的，
  因此「进程在扣额后崩溃」「Kafka 投递成功但消费失败」「落库失败且补偿也失败」都能被对账发现并回补额度。
- 回补必须**幂等**：Kafka 失败回调与对账任务可能同时判定同一单失败，
  若不去重会重复 `INCR` 造成超发。实现上用 `resv:compensated:{orderNo}` 做一次性标记。

> **超卖恒为 0 的依据**：Redis 是额度的权威持有者，扣减是原子的；
> DB 落库失败 → 回补 Redis 额度；回补失败 → 对账兜底。任一环失败都不会出现「同一份额度被两个人占用」。

### 4.2 百万并发支撑（峰值路径 = 校验 + 原子扣额度）

开闸瞬间的百万并发全部压在**提交**这一条路径上，因此必须让这条路径**极短、无 DB、无锁竞争**：

| 手段 | 说明 |
|------|------|
| 网关多级限流 | 全局总限流 → IP 限流 → 用户限流（Sentinel + Redis 分布式计数） |
| 无状态水平扩展 | gateway / reservation 服务按 QPS 横向扩容 |
| **额度按网点分配** | 额度天然按「商品 × 网点」隔离，全局热点被拆成 N 个网点级小热点（真实银行就是这么做的） |
| **网点额度分片** | 单个网点的额度再拆 N 个分片，**扣减起点按身份证哈希错开**，把同一网点的并发摊到 N 个 key |
| 限购计数分片 | 限购 Hash 按 productId 组织，`idCard` 为 field，无需跨 key |
| 活动时间窗本地缓存 | 开闸/截止时间定时拉进本地内存（`ActivityWindowCache`），**提交时零远程调用** |
| 资格校验 | 实名结果预先写入 Redis（`qual:ok:{userId}`），提交时一次 `EXISTS` |
| 幂等去重 | 一次 `SET NX EX`，失败立即释放 |
| Redis Cluster | 分片 + 主从，读写分离，故障自动切换 |
| Kafka 削峰 | 预约结果异步写 Kafka 落库，DB 压力与峰值解耦 |

> **关键**：峰值路径 = `时间窗校验(内存) → 幂等(1 次 SET) → 资格(1 次 EXISTS) → 额度扣减(1 次 Lua) → 落 Kafka(异步)`，
> 全程不碰数据库、不排队等待、无跨 key 事务。单实例可支撑数万~十数万 QPS，水平扩展达成百万级。

### 4.3 先到先得（排队）单模式

普通纪念币只有一种分配语义：**先到先得、约满为止**。没有抽签模式，也没有独立的分配阶段。

| 环节 | 实现 |
|------|------|
| 顺序如何确定 | **不由队列决定，而由扣减成功的先后决定**——Lua 脚本原子扣到额度的那一瞬间，预约即成立 |
| 排队号 | 扣减成功后 `INCR resv:seq:{productId}` 得到「该产品第 N 位预约成功者」，随结果落库 |
| 失败语义 | 必须精确到**网点级**：`1001 该网点已约满`，前端据此引导用户改选其它网点 |
| 余量可见 | `GET /api/reservation/stock/{productId}` 返回各网点余量，让用户提交前就能避开已约满的网点 |

> 原始 v2.0 设计曾用「Redis Sorted Set 排队池 + 定时分配器 `ZPOPMIN`」来实现排队模式，
> 但那会带来两个真实业务下不可接受的问题：
> ① 用户当场拿不到结果（只拿到「已受理」），违背「先到先得」的体验；
> ② 分配阶段若某成员所选网点已满，该成员会被**跳过**，而真实业务中用户是在**选网点时**就知道满没满、可以立刻换一家。
> 因此 v3.0 把「扣额度」直接并入 `submit`，**取消排队池、抽签池与分配器**。

#### 真实银行是怎么扛住峰值的（同构手段）

- **错峰放号**：如工行 2026 年贺岁币 22:00 开闸、贺岁钞 22:30 开闸，故意错开半小时；
- **额度按网点切分**：全局热点拆成网点级小热点；
- **预约入口提前开放**：让用户提前进入填单页，开闸瞬间只提交；
- **强限流 + 限额**（每人限约一次、限 20 枚）。

### 4.4 限流与降级（Sentinel）
- 网关层：QPS 限流、并发线程数限流、热点参数限流（对 hot 商品 ID）。
- 预约服务层：Sentinel 熔断 Redis/Kafka 异常，快速失败，避免雪崩。
- 降级策略：资格校验失败直接拒绝；Redis 不可用时切「DB 直扣」并强限流（见 4.6），
  **降级链路与主链路的返回语义一致**——同样是「提交即占额度、当场返回预约号」，
  用户拿到的结果含义不变，只是吞吐下降。

### 4.5 事务回滚与分布式一致性（核心）

**先认清本质**：Redis 与 PostgreSQL 是两种独立存储，Redis 不支持 ACID，也不参与 XA 分布式事务。因此 **「Redis 与 PG 一起回滚」无法用数据库事务实现**，只能分层处理：

| 边界 | 机制 | 是否「真回滚」 |
|------|------|---------------|
| PostgreSQL 内部（落库事务） | 本地 ACID 事务（`@Transactional`） | ✅ 真回滚（rollback） |
| Redis 内部（扣额度 + 扣限购） | Lua 原子脚本 | ✅ 原子，无中间态 |
| Redis ↔ PostgreSQL 跨库 | **在途单 + 幂等补偿 + 对账** | ⚠️ 补偿式回滚，最终一致 |

#### 预约单状态机（贯穿 orderNo）
```
SUBMITTED（Redis 已扣额度+限购，已记在途单，用户已拿到预约号）
     │  发 Kafka RESV_RESULT
     ▼
order-service 落库
     ├─ PG 事务成功 ──────────▶ CONFIRMED（t_reservation 已落库）
     └─ PG 事务失败/超时 ──────▶ COMPENSATED（Redis 已回补额度+限购）
```

#### 一致性完整流程
```
reservation-service 的 submit():
  ① Lua 扣 Redis「网点额度 + 限购」→ 成功 → 生成 orderNo（预约号）→ 状态 SUBMITTED
  ② INCR 取预约顺序号
  ③ 记在途单 resv:pending:{productId}（存完整消息 JSON）   ← 必须在投递之前
  ④ 发 Kafka RESV_RESULT
  ⑤ 当场返回 orderNo + 网点剩余额度给用户
order-service 消费:
  ⑥ 开 PG 本地事务:
       UPDATE t_branch_stock SET remain=remain-1, version=version+1
        WHERE product_id=? AND branch_id=? AND remain>0
       INSERT t_reservation（唯一约束兜底）
     - 成功 → COMMIT → 状态 CONFIRMED
     - 失败 → ROLLBACK（ACID 自动回滚）→ 状态 COMPENSATED
  ⑦ PG 事务失败 → 触发「Redis 补偿」回补额度 + 回退限购
```

> 第 ③ 步在投递**之前**是刻意的：若进程在扣额之后、投递之前崩溃，
> 额度在 Redis 里已被扣掉但没有任何落库记录——只有先写好在途单，对账才能发现并回补。
> 代价是「投递失败回调」与「对账任务」可能同时判定同一单失败，因此补偿必须幂等（见下）。

#### PostgreSQL 回滚（本地事务，ACID）
```java
@Transactional(rollbackFor = Exception.class)
public void confirm(ReservationResultMessage msg) {
    int updated = branchStockRepository.deduct(msg.getProductId(), msg.getBranchId()); // remain>0 条件，0 行 → 抛异常回滚
    if (updated != 1) {
        throw new BizException(ResultCode.STOCK_EMPTY);
    }
    reservationRepository.save(r);   // 唯一约束 (product_id, id_card) 冲突 → 抛异常回滚
    // 方法正常返回 → COMMIT；抛异常 → 两条语句一起 ROLLBACK
}
```

#### Redis 回滚（补偿 Lua，与扣减脚本严格对称）
```lua
-- 补偿：额度 +1，限购 -1（仅当该用户确实扣过才执行）
redis.call('incr', KEYS[1])                 -- 网点额度回补
redis.call('hincrby', KEYS[2], ARGV[1], -1) -- 限购回退
```

#### 关键风险与规避（最容易被忽略的点）

**风险**：PG 事务已 COMMIT 成功，但响应超时 → 触发补偿回补了 Redis → 结果 PG 里有一单、Redis 额度却被加回 → 超卖 1 个。

**规避（四道保险）**：
1. **PG 是最终真相**：`t_reservation` 唯一约束 `(product_id, id_card)` 拒绝重复；`t_branch_stock.remain>0` 乐观条件拒绝网点超扣——PG 层永远不会超卖。
2. **补偿前先查 PG**：回补 Redis 前先查 `t_reservation` 是否已存在该 `orderNo`，已存在则**不回补**（说明 PG 实际成功）。
3. **幂等补偿**：回补前用 `resv:compensated:{orderNo}` 做一次性标记（`SET NX`），
   确保「Kafka 失败回调」与「对账任务」并发触发时**只真正回补一次**——
   这是从「先记在途单再投递」这一步引入的新并发点，必须显式去重，否则重复 `INCR` 会造成超发。
4. **定时对账兜底**：扫描在途单中超时未确认的 orderNo → 查 PG → 未落库则回补 Redis，已落库则移出在途集合。

#### 失败场景回滚矩阵

| 失败点 | PostgreSQL 动作 | Redis 动作 |
|--------|----------------|-----------|
| ① Lua 扣减失败（该网点额度尽/重复预约） | 不涉及 | 无副作用（Lua 内原子判断后直接返回）；**释放幂等键**使用户可换网点重试 |
| ② 投递前进程崩溃 | 无记录 | 在途单保留 → 对账查 PG 发现未落库 → 幂等回补 |
| ③ Kafka 投递失败/超时 | 不涉及 | 幂等回补额度 + 限购，并撤在途单 |
| ④ PG 落库失败（唯一冲突/额度0/DB 挂） | 事务自动 ROLLBACK | 幂等回补额度 + 限购 |
| ⑤ PG 提交成功但响应超时 | COMMIT 已生效 | 先查 PG，已落库则**不回补**，仅移出在途集合 |
| ⑥ 消费端重复消费 | 唯一约束拒绝重复 | 幂等，不重复回补 |
| ⑦ 补偿本身失败 | 无影响 | 删除补偿标记 + 保留在途单，交对账重试 |

> **一句话总结**：PostgreSQL 用「事务」做真回滚，Redis 用「补偿 Lua」做回滚，
> 两者之间靠「在途单 + 补偿前先查 + 幂等补偿 + 定时对账」保证最终一致，超卖恒为 0、额度不丢不重。

### 4.6 Redis 故障的 DB 兜底降级方案

**定位澄清（必须先说清）**：DB 兜底是**「降级保可用」，不是「替代 Redis 扛百万并发」**。单 PostgreSQL 主库写吞吐约 5000~1 万 TPS，与百万 QPS 相差 1~2 个数量级。因此 Redis 挂时必须三管齐下：
1. **强限流**：Sentinel 令牌桶把并发压到 DB 容量以内；
2. **业务降级**：提示「系统繁忙/请稍后再试」，必要时转为排队；
3. **绝不裸奔**：不让 DB 直接暴露在峰值流量下，否则 DB 必被打垮。

#### 单库 1主2从 + 不分库分表（当前架构）

- 写走**主库**，读走 **2 个从库**（预约明细查询、兑换查询等读多走从库）。
- 不分库分表 → 唯一约束 `(product_id, id_card)` 与乐观锁 `remain>0` 天然在**单库内**成立，防超卖/防超限购无需跨库处理。
- **单库最大优势**：「扣网点库存 + 写预约记录」在**同一个数据库事务**内完成，一致性实现最简单、最可靠（无需分库分表下的跨库补偿）。

#### DB 直扣防超卖（降级模式，单库事务）
```sql
-- 同一事务内：
-- 1) 网点库存扣减：乐观条件，affected=0 → 该网点已约满
UPDATE t_branch_stock
   SET remain = remain - 1, version = version + 1
 WHERE product_id = ? AND branch_id = ? AND remain > 0;

-- 2) 写预约记录：唯一约束冲突 → 该身份证已约过（防超限购）
INSERT INTO t_reservation(order_no, product_id, branch_id, user_id, id_card, status, create_time)
VALUES (?, ?, ?, ?, ?, 1, now());
-- 任一失败 → 事务整体回滚，无需跨库补偿
```

#### 切换与恢复流程（✅ 已实现，见下方实现映射）
```
① 检测：Sentinel/健康检查判定 Redis 不可用
② 切换：网关/服务自动切「DB 直扣」降级模式 + 强限流（压到主库容量内）
③ 运行：主库单库事务直扣 PG，防超卖靠乐观锁 + 唯一约束；**返回语义与主链路一致（同样是「提交即占额度、当场返回预约号」）**
④ 恢复：Redis 恢复后，用 PG 数据重建 Redis 额度与网点清单（对账），切回 Redis 主模式
```

**实现映射**（`coin-reservation-service`）：

| 步骤 | 实现 | 关键类 / 配置 |
|------|------|--------------|
| ① 检测 | Redis 超时配置（500ms）+ 异常识别（`DataAccessException`/Redis 异常）+ 降级状态标记 | `application.yml: spring.data.redis.timeout`、`ReservationService.isRedisUnavailable()`、`DegradeManager.markRedisDown()` |
| ② 切换 | 手动开关（Nacos 动态）+ Redis 故障自动切换；`Sentinel` 对降级直扣做强限流 | `DegradeManager`（`@RefreshScope` + `coin.degrade.db-direct-enabled`）、`SentinelRuleConfig`（`dbDirectSubmit` 限流 + `reservationSubmit` 熔断） |
| ③ 运行 | 单库事务直扣：乐观锁 `remain>0` + 唯一约束 `(product_id,id_card)`，失败整体回滚 | `DbDirectReservationService.submitDirect()`（`@Transactional` + `@SentinelResource`） |
| ④ 恢复 | 降级状态下每 5s 探活；恢复后切回主模式并用 PG `remain` 重建 Redis 分片 | `RedisHealthProbe`、`StockRebuildService.rebuildAll()` |

**对账兜底**：`ReservationReconcileTask` 定时扫描**在途单** `resv:pending:*`（投递前写入），
超过阈值仍未落库则「先查 PG 确认未落库 → 幂等回补额度」，保证最终一致。

> **扫描方式用 SCAN 游标，而非 `KEYS`**：Redis 单线程执行命令，`KEYS` 会一次性遍历整个 key space
> 并在期间阻塞所有其它命令。本工程光网点额度分片 key（产品 × 网点 × 10 分片）就可能上万，
> 一次 `KEYS resv:pending:*` 足以拖垮整个集群。`SCAN` 按 `COUNT`（默认 500）分多批返回、不阻塞；
> 游标断开时本轮先处理已扫到的 key，剩余下轮补扫；重复 key（rehash 期间可能返回）用 Set 去重。

**运维接口**：
- `GET /api/reservation/degrade/status` 查看降级状态
- `POST /api/reservation/rebuild/{productId}` 手动重建 Redis 额度（同时刷新 `resv:branches:{productId}`）

> **已知边界**：重建以 PG `remain` 为准，若存在「Redis 已扣但尚未落库」的在途订单，重建会把该部分额度加回，造成 Redis 短暂多算；由 PG 乐观锁 + 唯一约束作为最终兜底（最坏是少数请求在落库阶段被拒，不会超卖）。

#### 单库下的容量与可用性对策
| 风险 | 对策 |
|------|------|
| 主库写单点 | 自动故障切换（Patroni / Repmgr），主挂切从，切换窗口秒~分钟级 |
| 写吞吐瓶颈 | 异步落库 + 最终一致；落库慢不影响预约成功率 |
| 单表膨胀 | 按活动/年度**归档历史数据**，控制单表体量 |
| 读压力 | 读走 2 从库；关键状态查询走主库，非关键走从库 |
| 主从延迟 | 关键一致性读走主库，避免读到旧状态 |

> **一句话总结**：Redis 挂了 → 降级为「DB 直扣 + 强限流」，单库事务（乐观锁 + 唯一约束）防超卖；单库保「正确性」最简，瓶颈只在「写吞吐 + 写单点」，靠异步落库 + 归档 + 主从切换缓解。

## 五、业务流程设计（三阶段 + 下游）

### 阶段 0：活动准备（预热）
1. product-service 发布活动，配置**各网点额度**、**开闸/截止时间**、限购（每人限约一次）。
2. 网点额度（商品 × 网点）按分片写入 Redis，**并登记该产品的可预约网点清单**（`resv:branches:{productId}`）。
3. 产品/网点信息预热进本地缓存；活动时间窗（开闸/截止）由 `ActivityWindowCache` 定时拉进内存。

> 真实业务的预约入口会在正式开闸前开放（让用户提前填单），系统在开闸前统一拒绝提交：
> 早于 `submit_start` 返回 `1008 活动尚未开始`，晚于 `submit_end` 返回 `1009 活动已结束`。

### 阶段 1：实名预填（开闸前）
```
用户提交实名(姓名/身份证/手机) → user-service 三要素校验 → 写入 t_qualification(唯一索引 id_card)
                                                              → Redis 标记已实名 qual:ok:{userId}
```
- 未实名预填通过的用户，开闸时无法提交预约。

### 阶段 2：提交预约（开闸瞬间 = 百万并发峰值，**同步扣额度、当场出结果**）

```
客户端 → gateway(鉴权+限流) → reservation-service
  1. 活动时间窗校验（本地缓存，不查库）
  2. 幂等去重(SETNX token)                  ← 失败即释放，成功才保留
  3. 资格校验：已实名预填 ✓
  4. Lua 原子扣「所选网点」额度 + 限购       ← 先到先得的胜负就在这一步
        -1 该网点额度尽 → 返回 1001「该网点已约满」（前端引导换网点）
        -2 已约过       → 返回 1002「超过限购数量」（重复预约无效）
  5. 生成 orderNo（预约号）+ INCR 取预约顺序号 sequenceNo
  6. 记在途单 resv:pending:{productId} → 发 Kafka RESV_RESULT（异步落库）
  7. **同步返回 orderNo + 网点剩余额度** ──▶ 用户此刻已知晓「约上了」
```

- 本阶段**不写 DB**（纯 KV + 一次 Lua），但**必须扣额度**——因为「提交成功」就是「预约成功」。
- 响应示例：`{"code":0,"data":{"orderNo":"1856…","sequenceNo":1024,"branchId":1,"branchRemain":287,"status":1}}`

### 阶段 3：预约落库（异步、幂等）

```
order-service 消费 Kafka RESV_RESULT
  → 幂等校验(orderNo 已存在则直接 ack)
  → 单库事务：更新 t_branch_stock(乐观锁 remain>0) + INSERT t_reservation(唯一索引兜底)
  → 失败：事务回滚 → 幂等回补 Redis 额度（见 4.5）
  → 前端随后可查：GET /api/order/list?idCard=xxx（含 orderNo / sequenceNo / 状态）
```

- 落库只影响「能否查到、能否兑换」，不影响「是否约上」——额度的权威记录在 Redis。
- **已知窗口**：若 Kafka 通道最终投递失败，会回补额度，此时用户虽已看到「预约成功」但实际未约上。
  该窗口由 Kafka `delivery.timeout.ms`（3s）界定，仅在后端消息通道故障时出现。

### 阶段 4：兑换（线下柜面）

```
exchange-service:
  校验 orderNo + idCard + branchId + 状态=1 已预约
  → 标记 3 已兑换，写 t_exchange 兑换流水
  → 重复兑换返回 1010
```

### 待补齐（真实业务存在、本工程尚未建模）

| 环节 | 真实规则 | 当前状态 |
|------|---------|---------|
| **人民银行核查期** | 预约期结束后人行对全量预约记录核查：**在两家以上承办银行重复预约**、**往期已预约未兑换**的客户核查不通过，需在核实期内到网点办理保留兑换资格 | ❌ 未实现。跨行重复必须依赖人行统一系统，单家银行只能查本行 `t_reservation` |
| **兑换期** | 预约成功后须在指定兑换期内到预约网点兑换，逾期作废 | ❌ 未实现（仅有兑换登记，无兑换期校验/逾期作废） |
| **违约记录** | 预约成功未兑换会被记录，影响下一次普通纪念币预约兑换 | ❌ 未实现。状态字典中也没有「未兑换/违约」，缺少跨活动的违约累计 |
| **余量兑换** | 前序未兑换释放出的额度，再放一轮供公众预约 | ❌ 未实现 |
| **预约修改/撤销** | 预约期内可修改数量或网点（**需先释放已预约额度再抢约**）、可撤销 | ⚠️ 有设计（5.5.3）但未实现 |

### 异常与兜底矩阵

| 场景 | 处理 |
|------|------|
| Redis 挂/超时 | Sentinel 熔断 + 切「DB 直扣」降级模式（见 4.6），强限流保可用；返回语义与主链路一致 |
| **扣额度命令超时（可能已在服务端生效）** | **绝不降级为 DB 直扣**——否则 Redis 与 DB 各占一份额度即重复预约。改为返回「系统繁忙」，保留幂等键让用户重试时得到「请勿重复提交」并引导其查询预约结果 |
| 提交时该网点已满 | 返回 `1001`（网点级原因），释放幂等键，用户可立即改选其它网点 |
| Kafka 不可用 | 生产者本地重试（retries=3）+ 投递失败幂等回补额度；在途单保留供对账 |
| 进程在扣额后崩溃 | 在途单已先落 Redis → 对账查 PG 未落库 → 幂等回补额度 |
| DB 写入失败 | PG 事务 ROLLBACK + Kafka 消费重试 + 幂等回补（先查 PG 后补） |
| 重复请求/网络重试 | 幂等 Token + 预约单唯一约束双保险 |
| 补偿被并发触发 | `resv:compensated:{orderNo}` 一次性标记，保证只回补一次（不超发） |
| 分片不均 | 扣减起点按身份证哈希错开；定时对账 Redis vs PG 额度 |
| **Redis 重建与在途单冲突** | 重建以 PG `remain` 为准，会把「已扣未落库」的额度加回，造成 Redis 短暂多算；由 PG 乐观锁 + 唯一约束最终兜底 |

### 5.5 配套业务功能（查询 / 取消 / 修改 / 兑换）

预约单状态机：
```
1 已预约(待兑换) ──取消──▶ 2 已取消
1 已预约(待兑换) ──修改──▶ 4 已修改(原单作废，生成新单/更新网点)
1 已预约(待兑换) ──兑换──▶ 3 已兑换
```

#### 5.5.1 预约明细查询（高频读）
- 按 `id_card` / `user_id` 查 `t_reservation`（单库查询）。
- 热数据走 Redis 缓存（`resv:detail:{orderNo}` / 按用户维度），读多写少。
- 提供：我的预约列表、单条详情、当前状态。

#### 5.5.2 预约取消（低频写）
- 前置校验：预约存在、状态=已预约、未兑换、**当前仍在预约期内**（真实业务仅预约期内可取消）。
- PG 事务：`UPDATE t_reservation SET status=2 WHERE order_no=? AND status=1`。
- 释放额度：网点额度 +1（Redis `INCR` / DB `remain+1`）+ 限购 -1（`HINCRBY -1`）。
- 一致性：与 4.5 同构（先改状态 → 幂等回补额度），取消后额度释放、可被他人约走。

#### 5.5.3 预约修改（低频写，主要是改网点）
- 本质：换网点 = **原网点额度回补 + 新网点额度扣减** + 更新 `branch_id`。
- 真实规则：**必须先释放已预约额度再重新抢约，可能存在预约失败风险**（额度可能已被别人抢走）——
  因此修改是「尽力而为」，不能保证成功。
- 防超卖：新网点可能已满，扣减失败 → 修改失败，原预约保持不变（不能先释放再失败，否则用户两头落空）。
- 限购：同一人，**不重复扣限购**，仅转移网点额度。
- 实现：Redis Lua 原子「新网点先判 >0 并 -1 → 成功再原网点 +1」；DB 侧用事务 + 乐观锁。
- 窗口限制：仅预约期内允许修改。

#### 5.5.4 预约兑换登记（线下柜面，低频）
- 柜员输入身份证/预约单号 → 查询预约 → 校验：**网点匹配、状态=已预约、未兑换**。
- PG 事务：`UPDATE t_reservation SET status=3` + `INSERT t_exchange`（兑换流水）。
- 防重复兑换：状态机 + `t_exchange` 唯一约束（order_no）。
- 独立 `exchange-service`（柜面渠道，权限隔离，与线上抢约流量解耦）。

## 六、数据模型设计（PostgreSQL）

```sql
-- 网点表（基础数据，通常由核心系统同步）
CREATE TABLE t_branch (
  id            BIGSERIAL PRIMARY KEY,
  branch_code   VARCHAR(32)  NOT NULL,
  branch_name   VARCHAR(128) NOT NULL,
  address       VARCHAR(256),
  status        SMALLINT NOT NULL DEFAULT 1,   -- 1营业 2停业
  CONSTRAINT uk_branch_code UNIQUE (branch_code)
);

-- 实名资格表（阶段1，唯一约束防重复）
CREATE TABLE t_qualification (
  id            BIGSERIAL PRIMARY KEY,
  user_id       BIGINT NOT NULL,
  id_card       VARCHAR(32) NOT NULL,
  name          VARCHAR(64) NOT NULL,
  phone         VARCHAR(20),
  status        SMALLINT NOT NULL DEFAULT 1,   -- 1校验通过 2未通过
  create_time   TIMESTAMP NOT NULL DEFAULT now(),
  CONSTRAINT uk_qualification_idcard UNIQUE (id_card)
);

-- 产品/额度表（总发行量；网点额度在 t_branch_stock）
CREATE TABLE t_product (
  id              BIGSERIAL PRIMARY KEY,
  product_code    VARCHAR(64)  NOT NULL,
  name            VARCHAR(128) NOT NULL,
  total_stock     BIGINT       NOT NULL,       -- 总发行量
  limit_per_user  INT          NOT NULL DEFAULT 1,
  submit_start    TIMESTAMP    NOT NULL,  -- 开闸(预约开始)
  submit_end      TIMESTAMP    NOT NULL,  -- 截止(预约结束)
  status          SMALLINT     NOT NULL DEFAULT 0,
  CONSTRAINT uk_product_code UNIQUE (product_code)
);

-- 网点库存表（商品 × 网点，乐观锁防网点超卖）
CREATE TABLE t_branch_stock (
  id            BIGSERIAL PRIMARY KEY,
  product_id    BIGINT NOT NULL,
  branch_id     BIGINT NOT NULL,
  total         BIGINT NOT NULL,               -- 该网点额度
  remain        BIGINT NOT NULL,               -- 该网点剩余
  version       BIGINT NOT NULL DEFAULT 0,     -- 乐观锁
  CONSTRAINT uk_branch_stock UNIQUE (product_id, branch_id)
);

-- 预约结果表（防超卖/防重复预约兜底：唯一约束）
CREATE TABLE t_reservation (
  id            BIGINT PRIMARY KEY,          -- 雪花ID（应用层生成）
  order_no      VARCHAR(64) NOT NULL,        -- 预约号
  product_id    BIGINT NOT NULL,
  branch_id     BIGINT NOT NULL,             -- 预约网点
  user_id       BIGINT NOT NULL,
  id_card       VARCHAR(32) NOT NULL,
  sequence_no   BIGINT,                      -- 预约顺序号（该产品第 N 位约上的人）
  status        SMALLINT NOT NULL DEFAULT 1, -- 1已预约 2已取消 3已兑换 4已修改
  create_time   TIMESTAMP NOT NULL DEFAULT now(),
  update_time   TIMESTAMP NOT NULL DEFAULT now(),
  CONSTRAINT uk_reservation_orderno UNIQUE (order_no),
  CONSTRAINT uk_reservation_product_idcard UNIQUE (product_id, id_card)  -- 跨网点一人一次
);

-- 兑换登记表（线下兑换流水，防重复兑换）
CREATE TABLE t_exchange (
  id            BIGSERIAL PRIMARY KEY,
  order_no      VARCHAR(64) NOT NULL,        -- 关联预约单号
  product_id    BIGINT NOT NULL,
  branch_id     BIGINT NOT NULL,             -- 实际兑换网点
  id_card       VARCHAR(32) NOT NULL,
  exchange_time TIMESTAMP NOT NULL DEFAULT now(),
  operator_id   BIGINT,                      -- 柜员ID
  status        SMALLINT NOT NULL DEFAULT 1, -- 1已兑换 2已撤销
  CONSTRAINT uk_exchange_orderno UNIQUE (order_no)
);
```

> **数据库架构：单库 1主2从，不分库分表**：
> - 写走主库，读走 2 从库（读写分离）。
> - 唯一约束 `(product_id, id_card)` 与乐观锁 `remain>0` 在单库内成立，防超卖/防超限购无需跨库处理。
> - 单表体量靠**数据归档**控制（按活动/年度归档历史预约、兑换记录）。
> - 主从切换用 Patroni / Repmgr 自动故障转移。
>
> **隔离级别**：落库事务默认 `READ COMMITTED`，配合乐观锁 `version` + 唯一约束即可满足，无需 `SERIALIZABLE`（避免性能损失）。

## 七、Redis Key 设计

| Key | 类型 | 说明 | TTL |
|-----|------|------|-----|
| `stock:{productId}:{branchId}:{shardId}` | String | 网点额度分片计数（商品 × 网点 × 分片） | 活动期 |

## 八、Kafka 消息设计

| 项 | 设计 |
|----|------|
| Topic | `RESV_RESULT`（预约成功结果落库） |
| 消息体 | `{messageId, orderNo, productId, branchId, userId, idCard, sequenceNo, shard, timestamp}` |
| Key | `orderNo`（保证同单分区内有序 + 幂等） |
| 消费组 | `order-consumer-group`（order-service 集群消费） |
| 分区 | 按峰值落库吞吐规划（如 16/32 分区） |
| 可靠性 | producer `acks=all` + `retries=3` + 消费端幂等；**无事务消息，用「在途单 + 失败回补额度」替代** |
| 幂等 | 消费端以 `orderNo` 去重 + DB 唯一索引 |
| `shard` 字段用途 | 回补时精确定位到「当初扣减的那个分片」，避免回补到错误分片导致额度失真 |

> **Kafka 替代 RocketMQ 的说明**：Kafka 无原生事务消息，因此「扣额度成功 → 发消息」采用 **补偿式可靠投递**：
> 投递前先写**在途单**，投递失败/超时 → 幂等回补额度（Lua INCR）+ 定时对账，配合消费端幂等，等价达到最终一致。
>
> **落库与「预约成功」的关系**：用户看到「预约成功」的依据是 Redis 扣额成功，落库只是写镜像。
> 若消息通道最终故障导致回补，会出现「用户已看到成功但实际未约上」的窗口（上限 = Kafka
> `delivery.timeout.ms`，当前配置 3s）。要彻底消除需改为提交时同步等待落库确认，用延迟换确定性。
